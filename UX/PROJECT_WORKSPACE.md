# Área de Trabalho do Projeto

## Objetivo

Cada projeto terá uma área isolada dentro do SSC Mission Control.

Essa área concentrará todas as informações necessárias para planejar, desenvolver, testar, publicar e evoluir o software.

## Cabeçalho do projeto

O cabeçalho deverá exibir:

- Nome do projeto
- Código interno
- Estado atual
- Versão
- Progresso
- Responsável
- Prioridade
- Ambiente atual
- Último evento
- Último release
- Alertas ativos

## Estados principais

- IDEA
- DISCOVERY
- WAITING_APPROVAL
- PLANNING
- DEVELOPMENT
- TESTING
- STAGING
- PRODUCTION
- EVOLUTION
- PAUSED
- ARCHIVED

## Navegação interna

A área do projeto deverá possuir:

- Visão Geral
- Discovery
- Referências
- Requisitos
- Arquitetura
- Backlog
- Sprints
- Equipe
- Execuções
- Qualidade
- Segurança
- Knowledge Vault
- RFCs
- ADRs
- Releases
- Deployments
- Auditoria
- Configurações

## Visão Geral

A página inicial do projeto deverá apresentar:

- Objetivo
- Problema resolvido
- Estado atual
- Percentual de progresso
- Próximo marco
- Riscos
- Bloqueios
- Pendências de aprovação
- Atividades recentes
- Agentes trabalhando
- Último deployment

## Discovery

A seção Discovery deverá armazenar:

- Ideia original
- Contexto enviado
- Entrevistas
- Perguntas pendentes
- Discovery Report
- Revisões
- Aprovação humana
- Histórico de alterações

## Referências

A seção deverá permitir:

- Enviar arquivos
- Adicionar links
- Classificar referências
- Adicionar descrições
- Definir importância
- Consultar processamento
- Visualizar informações extraídas
- Relacionar referência com requisito
- Criar nova versão da referência

## Requisitos

Deverá apresentar:

- Requisitos funcionais
- Requisitos não funcionais
- Regras de negócio
- Casos de uso
- Histórias de usuário
- Critérios de aceite
- Dependências
- Prioridades
- Situação
- Origem do requisito

Cada requisito deverá ser rastreável até:

- Entrevista
- Referência
- Decisão
- Tarefa
- Teste
- Release

## Arquitetura

A seção deverá armazenar:

- Visão geral da solução
- Componentes
- Serviços
- Banco de dados
- APIs
- Eventos
- Integrações
- Diagramas
- Decisões arquiteturais
- Restrições técnicas
- Requisitos de infraestrutura

## Backlog

O backlog deverá ser organizado por:

- Épicos
- Funcionalidades
- Histórias de usuário
- Tarefas técnicas
- Bugs
- Melhorias
- Dívidas técnicas

Cada item deverá possuir:

- Identificador
- Título
- Descrição
- Prioridade
- Responsável
- Agente
- Situação
- Dependências
- Critérios de aceite
- Estimativa
- Sprint
- Histórico

## Sprints

Cada sprint deverá apresentar:

- Objetivo
- Data de início
- Data de encerramento
- Itens planejados
- Itens concluídos
- Bloqueios
- Entregas
- Retrospectiva
- Métricas

## Equipe

A seção deverá mostrar:

- Agentes alocados
- Função
- Modelo de IA
- Permissões
- Ferramentas
- Situação
- Tarefa atual
- Última execução
- Consumo de recursos

## Execuções

Cada execução deverá registrar:

- Identificador
- Projeto
- Agente
- Tarefa
- Data e hora
- Entrada recebida
- Contexto utilizado
- Ferramentas chamadas
- Comandos autorizados
- Arquivos alterados
- Resultado
- Logs
- Erros
- Duração
- Consumo de recursos
- Commit gerado

## Qualidade

A seção deverá apresentar:

- Testes unitários
- Testes de integração
- Testes de interface
- Testes de regressão
- Testes de desempenho
- Cobertura
- Falhas abertas
- Histórico de correções
- Critérios de qualidade

## Segurança

A seção deverá apresentar:

- Revisões de segurança
- Vulnerabilidades
- Severidade
- Dependências vulneráveis
- Segredos detectados
- Permissões excessivas
- Recomendações
- Correções
- Aprovações

## Knowledge Vault

O Project Knowledge Vault deverá armazenar:

- Ideia original
- Referências
- Entrevistas
- Requisitos
- Decisões
- Arquitetura
- Documentação
- Conhecimento do código
- Erros conhecidos
- Soluções anteriores
- Releases
- Lições aprendidas

## RFCs

Toda mudança relevante deverá gerar uma RFC contendo:

- Solicitação
- Motivação
- Impacto funcional
- Impacto técnico
- Riscos
- Dependências
- Estimativa
- Plano de implementação
- Plano de rollback
- Aprovação

## ADRs

Decisões arquiteturais deverão registrar:

- Contexto
- Decisão
- Alternativas
- Consequências positivas
- Consequências negativas
- Estado
- Responsável
- Data

## Releases

Cada release deverá conter:

- Versão
- Escopo
- Tarefas incluídas
- Bugs corrigidos
- Testes
- Revisão de segurança
- Documentação
- Changelog
- Aprovações
- Artefatos
- Tag Git

## Deployments

A seção deverá controlar:

- Ambiente de desenvolvimento
- Ambiente de homologação
- Ambiente de produção
- Versão implantada
- Data e hora
- Responsável
- Logs
- Migrações
- Health checks
- Resultado
- Rollback

## Auditoria

Toda ação deverá registrar:

- Usuário ou agente
- Ação
- Projeto
- Recurso afetado
- Data e hora
- Resultado
- Endereço de origem
- Identificador de correlação

## Configurações

O projeto poderá configurar:

- Repositório Git
- Branch principal
- Estratégia de branches
- Modelos de IA
- Agentes autorizados
- Ferramentas permitidas
- Limites de recursos
- Ambientes
- Integrações
- Políticas de aprovação
- Retenção de logs
